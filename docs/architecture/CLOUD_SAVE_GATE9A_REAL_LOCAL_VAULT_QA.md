## Verified SaveManager facts and hazard

`SaveManager.SAVE_DOMAINS` has eight permanent schema-v1 files and one device-only active-run `checkpoint`. `write_save_batch()` records *final desired values* in `user://transaction.journal`, then completes individual atomic writes on startup after a crash. Each single-file write may rotate its previous primary into `.backup`. This is appropriate for idempotent local reward commits, but it is NOT a reversible eight-file cloud restore or a durable *whole-account* pre-restore backup. Calling `read_save_data()` can repair a corrupt primary and therefore is **not** a read-only inspection API. A future naïve restore using `write_save_batch()` could replay already committed remote data at a restart, or replace a previous `.backup` sidecar. Gate 9A must not do that.

## What changes here

1. `scripts/managers/cloud_local_backup_vault.gd` is a disconnected `RefCounted` library; it is **not** an autoload, scene script, SaveManager modification or scheduled action. `prepare_local_pre_restore_backup()` is a future **manual, explicit-consent** entry point. It checks the Google account UID, pending transaction/write blocks, scene transitions, gameplay state, active run/checkpoint, and active run equipment loadout. It uses only `SaveManager` registry metadata for eight source paths. It must fail rather than heal/save/rewrite a primary.
2. It copies **exact binary file bytes** of eight permanent primaries plus existing `.backup` sidecars to `user://jade_cloud_pre_restore_vault_v1/pending_<random>/`. It refuses missing files, unknown/legacy/future schema versions, incomplete required fields, `.tmp`/`.rollback` sidecars, unsupported sizes, short reads and hash changes. The manifest contains the local owner UID, schema metadata, per-file byte size and SHA-256 (not a signature). Each copy is flushed and verified. Sources are hashed again before the manifest is sealed.
3. **Commit marker:** the fully verified `pending_*` directory is atomically renamed to a new `ready_*` directory. An interruption while writing leaves an unfinished **pending** directory but no ready record. Existing ready backups are never overwritten or deleted automatically, and checkpoint/transaction-journal files are never copied or modified. There is intentionally NO operation to replace any primary or to restore anything from a vault. All outputs report `upload_allowed=false`, `restore_allowed=false`.
4. `prepare_sandbox_backup_for_qa()` and its inspector are hard restricted to `JADE_GATE9_TEST_ONLY=1` and the disposable `user://jade_gate9_qa/` fixture directory, and cannot access the real save root. A new, independent GitHub Actions Windows runner uses the **same SHA256-pinned official Godot 4.7.2** as the existing main smoke workflow to create synthetic save files and test physical filesystem behavior. Faults are injected after 1–10 staged file copies; staged attempts cannot become ready, an existing ready record remains intact, corrupted ready bytes are rejected, restart/reopening inspection works, and source primary/sidecars remain unmodified. This is **genuine Godot file I/O** against a disposable runner, not a Node-only simulation or an Android device test.
5. The Node boundary tests inspect the actual SaveManager registry and verify that the new vault is not wired into production, cannot call save-write APIs, and has no deploy capability. They are structural regression tests, not a substitute for the Godot runtime test.

## Safety limitations / mandatory Gate 9B+ work

- **No real account save is copied by CI or during normal game execution**. The production method remains disconnected; if a user is missing any one of the eight permanent files, it fails closed rather than synthesizing an economic balance or erasing legacy data.
- **Not yet a crash-safe cross-device restore.** A normal active SaveManager writer can still race the eight-file backup *between* the last digest check and the atomic directory rename. Before any production restore UI is connected, introduce an audited global save-write barrier and account-stability guard which cover the complete backup → remote decision → local write lifecycle, including process death/restart. Also preserve a durable pre-restore backup and validate restored data using domain-owner APIs.
- No code here atomically swaps eight primaries, replays/migrates eight domain managers, reconcilies premium currency, verifies Play purchase receipts, merges devices, restores purchases, or validates signed server freshness. Raw local Pavilion `processed_grant_ids` may contain sensitive purchase tokens: **vault stays local in app-private `user://` storage only**, with no telemetry/upload, and must not be repurposed as a portable cloud payload. Do not log or share vault files. Any cross-device migration must use Gate 6's privacy-safe rules and a reviewed server ledger.
- In-process process-exit fault injection is not an Android kill -9 / low-memory test; byte flush is not an all-platform filesystem `fsync()` guarantee. Follow-on Android debug QA must test killed process during every journal rename and restore rollback, including old saves and real upgraded domain formats. A successful Gate 9A QA is **not** authorization to enable Cloud Save restore.
- The existing one-slot `.backup` per domain is separate from the new vaulted whole-account backup; older ready vault directories need an explicit retention/cleanup policy later, never silent deletion.
